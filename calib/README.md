# Calibration-aware квантование whisper-small (раздел 3)

Проверяем, помогает ли учёт активаций при квантовании весов в `whisper.cpp`.

## Коротко

- **Калибровка (C) не дала значимого выигрыша по WER** ни в Q4_1, ни в Q5_1, ни в одном наборе при декодировании с fallback.
- C снижает ошибку весов, взвешенную по активациям, на всех 192 линейных слоях: примерно на 33% относительно B и на 46% относительно A (отложенные статистики dev). Обычная ошибка весов у C при этом примерно на 10% выше, чем у B.
- Размер калибровки (20 / 50 / 200 файлов) почти ни на что не влияет.
- **Q5_1:** значимых отличий от FP16 по WER не обнаружено (это не доказывает эквивалентность); файл в 2.6 раза меньше.
- **Q4_1:** файл в 3.0 раза меньше, но на RU WER значимо хуже FP16 у всех трёх вариантов (+2.3–3.7 п.п.).
- На нашем CPU обе схемы **медленнее FP16**: Q4_1 на 16–18%, Q5_1 на 31–32%.

## Варианты

| Модель | Квантование |
|---|---|
| FP16 | `ggml-model.bin`, без квантования |
| A | штатный min-max (`quant_weights = nullptr`) |
| B | оптимизатор GGML, все веса равны 1 |
| C | оптимизатор GGML, веса `E[x_j²]` по входным каналам |

Квантуются все 193 двумерных тензора. Статистики есть для 192 линейных слоёв; `decoder.token_embedding` в C получает единичные веса. `conv1.bias`, `conv2.bias` и позиционные эмбеддинги пропускаются, как в штатном квантизаторе.

Статистики: forward-hook на `nn.Linear` в HF-модели; `E[x_j²]`, делённое на среднее по каналам. Кадры паддинга отброшены во всех слоях, которые получают выход энкодера: в энкодере и в `cross_attn.key/value` декодера (тишина внутри записи оставлена). Токены декодера получены через `generate`.

### 2. Данные и эксперимент

Из `whisper.cpp/`:

```bash
python ../calib/prepare_data.py --out ../../asr_data
nohup bash ../calib/run.sh > run.log 2>&1 &
```

`run.sh` собирает статистики на калибровке и на dev (dev - только для ошибки по слоям), квантует A/B/C в Q4_1 и Q5_1 и проверяет, что статистики применились ко всем 192 слоям, затем считает ошибку по слоям, оценивает все модели на GPU в двух режимах, замеряет CPU (`CPUS=8,9,10,11` по умолчанию, номера ядер проверить через `lscpu -e`) и запускает абляцию. В конце лога - `ALL DONE`.

Не запускайте одновременно другой `evaluate.py` на тех же аудио: временные `.txt` пишутся рядом с ними.

## Протокол

- **Калибровка:** 100 EN (LibriSpeech clean `train.100`) и 100 RU (Golos farfield train), не более 2 файлов на спикера, если спикер указан.
- **Dev:** по 150 файлов LibriSpeech dev-clean и dev-other, 500 Golos farfield validation. Записи длиннее 30 с и без текста пропущены. Совпадения аудио калибровки и dev проверяются по SHA-1.
- **Источники:** `openslr/librispeech_asr` и сторонняя HF-копия Golos `bond005/sberdevices_golos_100h_farfield`.
- **Декодирование:** greedy (`-bs 1 -bo 1 -nt`), без VAD, язык задан явно. Режим без fallback добавляет `-nf`.
- **Нормализация:** EN через `EnglishTextNormalizer` из Whisper; RU: нижний регистр, `ё`→`е`, без пунктуации. Числа в RU не преобразуются.
- **Метрики:** WER/CER по корпусу; 95% интервалы парным bootstrap по фразам (10000, seed 42). Поправки на множественные сравнения нет.
- **RTF:** `(total − load) / длительность аудио`. Это не потоковая задержка.
- **Железо:** NVIDIA A100 80GB; Intel Xeon Gold 6338, 4 потока, закреплённые на ядрах `taskset`. Сервер общий. Сборка Release, `GGML_CPU_REPACK=ON`, `GGML_LLAMAFILE=OFF`.

Fallback добавлен после того, как на dev обнаружились зацикливания. Какой режим считать основным, **нужно согласовать с командой**. Ниже показаны оба.

### Значимость

- **B против A и C против B:** значимой разницы нет ни в одном формате, режиме и наборе.
- **C против A:** с fallback значимой разницы нет нигде (Q4_1 RU −1.22 [−3.12; +0.66], Q5_1 RU −0.77 [−1.80; +0.26]). Без fallback Q4_1 C лучше A на RU: −9.32 [−22.05; −0.87], в основном из-за зацикливаний A.
- **Q4_1 → Q5_1, RU с fallback:** WER ниже на 3.65 (A), 2.40 (B) и 3.20 п.п. (C), все три интервала не включают ноль. На EN значимой разницы нет.
- **Против FP16:** см. таблицу ΔWER. Без fallback значимо хуже также Q4_1 B на EN other (+0.80 [+0.11; +1.53]) и все Q4_1 на RU.

Поправки на множественные сравнения нет.

### Ошибка весов по слоям

Взвешенная ошибка: `Σ_j s_j·err_j / Σ_j s_j·ref_j`, где `s_j = E[x_j²]`, а `err_j` и `ref_j` — суммы квадратов ошибки и исходных весов по входному каналу. Это диагональное приближение ошибки выхода слоя; сами выходы не измерялись. Ниже геометрическое среднее отношений по 192 слоям, **меньше 1 лучше**. «Отложенная» метрика использует статистики dev из тех же корпусов.

| Формат | Метрика | B/A | C/A | C/B | C лучше B |
|---|---|---|---|---|---|
| Q4_1 | обычная | 0.795 | 0.877 | 1.102 | 0 / 192 |
| Q4_1 | отложенная | 0.809 | 0.543 | 0.671 | 192 / 192 |
| Q5_1 | обычная | 0.796 | 0.874 | 1.098 | 0 / 192 |
| Q5_1 | отложенная | 0.809 | 0.544 | 0.672 | 192 / 192 |

По отложенной метрике C/B в энкодере 0.743, в декодере 0.632 (Q4_1).

### Воспроизводимость сборки C

Статистики на 200 файлах собраны дважды (основной запуск и абляция): расшифровки C и C_cal200 совпали во всех 800 файлах. В более ранних запусках две такие сборки расходились до 0.4 п.п. WER на RU (вероятно, из-за недетерминированности вычислений на GPU), поэтому различия такого порядка не считаем преимуществом метода. Контрольные суммы моделей и `stats.bin` — в `results/sha256.txt`.

## Ресурсы

| Модель | Файл, МиБ | VRAM, МиБ | Пиковый RSS на CPU, МиБ | CPU RTF | Время к FP16 |
|---|---|---|---|---|---|
| FP16 | 465.0 | 1188 | 762 | 0.569 | — |
| Q4_1 A / B / C | 152.9 | 876 | 450 | 0.663 / 0.670 / 0.663 | +16–18% |
| Q5_1 A / B / C | 181.3 | 904 | 478 | 0.750 / 0.750 / 0.748 | +31–32% |

- **CPU:** Xeon Gold 6338, 4 потока на 4 физических ядрах, с fallback, по 17 файлов из каждого из трёх наборов, медиана 3 повторов по каждому набору, затем среднее с учётом длительности. WER этого маленького поднабора в сравнения не входит.
- **RSS** — пиковая память процесса `whisper-cli` (через отдельный маленький процесс-обёртку). На GPU — около 420–430 МиБ у всех моделей: веса лежат в видеопамяти.
- **VRAM** — память процессов `whisper-cli` по `nvidia-smi --query-compute-apps`, опрос каждые 0.2 с.
- **GPU:** RTF 0.014–0.019 для всех моделей, один прогон на модель; это не замер скорости с повторами.
- **Почему квантованные модели медленнее на CPU:** причина не установлена, профилирование не проводилось. На одном файле (`jfk.wav`) у Q4_1 A энкодер был медленнее FP16, а декодер быстрее.
- RTF меньше 1 **не подтверждает** потоковую работу в реальном времени: окно энкодера Whisper равно 30 с, задержка в потоке не измерялась.

## Выбор конфигураций (предварительный)

1. **Основная: Q5_1 A** (штатное квантование): на dev не хуже FP16 по WER при файле в 2.6 раза меньше. C и B не дали значимого выигрыша, поэтому дополнительные шаги калибровки здесь не оправданы. Если команда хочет показать метод раздела 3, Q5_1 C допустима: точечно лучшие WER, но выигрыш над A не доказан.
2. **Минимальный размер: Q4_1** — только если размер важнее качества: на RU она значимо хуже FP16 при любом варианте квантования.

**Итог раздела 3:** calibration-aware квантование снижает прокси-ошибку слоёв примерно на треть, но на dev это не переходит в значимое улучшение WER.

## Ограничения и что не сделано

- Нет прогонов на тестовых наборах.
- Нет измерений энергопотребления.
- Нет сравнения с исходной PyTorch-моделью на GPU и CPU.
- Поколоночный тест осей `test_axis.py` проверяет только Q4_1.
- Разброс скорости между повторами не сохраняется.
- `evaluate.py` не проверяет, что число ядер в `--cpus` не меньше числа потоков.
- Выбор конфигураций и режима декодирования сделан по dev.
